# Подключение к настоящей игре

## Что известно и чего пока нет

Локальное исследование GOG 1.61 уже выполнено: Mono/x64, Unity 2020.3.23f1,
загрузка BepInEx и чтение первой подсказки через NVDA подтверждены.
Сигнатуры, отпечатки и границы результата — в [GAME_API.md](GAME_API.md).
Следующие разделы описывают повторяемый процесс для новых экранов и сборок.

Unity подтверждён [разработчиком](https://steamcommunity.com/app/1199030/discussions/0/2514645967866651680/).
Windows inventory внешнего Steam depot даёт полезные ориентиры: `TG.Main.dll`,
`Assembly-CSharp.dll`, Rewired, TMP, I2, A* и Mono. Это вторичный источник,
не исследование пользовательской установки; подробности в
[game-evidence.md](research/game-evidence.md).

В публичных исходниках нет игровых DLL и декомпиляции. В версии 0.1.1 найден
точный observation target TitleScreen.LateUpdate для пассивного чтения;
в 0.1.3 подключён ограниченный стартовый input host с живыми Rewired maps,
original-handler scope и EventSystem guards. Он требует точные SHA-256/MVID
и явный EnableTitleInput. Меню/повтор/возврат проверены с NVDA; полный результат
и границы — в M1_VERIFICATION.md. История исследования 0.1.2 сохранена в
research/title-input-bindings.md.
Профиль `unbound.example.json` содержит
нулевые сведения о совместимости. Его нельзя включать как готовый профиль.

## Шаг 1. Инвентаризация без изменения игры

```powershell
py -3 .\scripts\inspect_game.py --game-dir "D:\Games\Tainted Grail"
```

При наличии точного Steam-манифеста:

```powershell
py -3 .\scripts\inspect_game.py --game-dir "D:\SteamLibrary\steamapps\common\Tainted Grail" --appmanifest "D:\SteamLibrary\steamapps\appmanifest_1199030.acf"
```

Проверяются PE architecture, CLI header/metadata, runtime markers и SHA-256
выбранных файлов. Скрипт не загружает assemblies в процесс, не запускает exe,
не ищет по дискам и не пишет внутрь игры. Отчёт содержит относительные пути.
`metadata_runtime_string` — метаданные CLR, не версия игры и не версия Unity.

Если известны одновременно сильные признаки Mono и IL2CPP, результат ambiguous.
Не удалять файлы ради принудительного нужного результата. Выяснить, не смешались
разные установки, старые loaders, иной магазин или ветвь игры.

## Шаг 2. Загрузчик и доказательство runtime

Для подтверждённого Mono исходный host нацелен на BepInEx 5. Его
[официальная инструкция](https://docs.bepinex.dev/articles/user_guide/installation/index.html)
отдельно оговаривает архитектуру процесса. Для IL2CPP существует
[другая инструкция](https://docs.bepinex.dev/master/articles/user_guide/installation/unity_il2cpp.html)
и другой API BepInEx 6. Эти ветви несовместимы на уровне bootstrap.

Точные версии loader/Unity/TFM фиксируются после проверки, а не выбираются по
номеру из случайного руководства. Не скачивать loader под The Fall of Avalon.
Существующий mod loader сначала идентифицировать; не устанавливать два одновременно.

После запуска записать в local profile:

- storefront и связь executable с игрой;
- runtime/architecture и Application.unityVersion;
- Application.version, Steam build ID при наличии;
- версии loader и bridge, SHA-256/MVID основных сборок;
- факт загрузки diagnostic plugin и результат настоящего speech check.

## Шаг 3. Сигнатуры и локальная декомпиляция

В диагностическом cfg включить `Diagnostics.ExportAssemblyInventory=true` и
перезапустить игру. Флаг одноразовый. Экспорт пишет только названия типов,
полей/свойств/методов и сигнатуры allowlisted assemblies, не значения, сцены
или сохранения. Ограничение размера и количества строк защищает от огромного dump.

Начать с TG.Main и Assembly-CSharp; не ограничиваться одной «привычной» DLL.
Экспорт может выполниться до загрузки нужной сборки: пустой результат требует
позднего явного повторного capture, а не выдумывания структуры.

ILSpy/dnSpyEx применяются к локальным файлам для выяснения модели/handlers.
Сигнатура — гипотеза до наблюдения настоящего UI вызова. Ищутся:

1. Владельцы start/menu/settings/dialogue/combat/target/reward/exploration UI.
2. Истинные признаки активности, readiness, loading и input locks.
3. Коллекции **экземпляров** карт, entities и legal targets, stable IDs.
4. Локализованные подписи, отображаемая цена и tooltip generation.
5. Методы, вызываемые визуальной активацией; guard недостатка ресурса/состояния.
6. InputManager/Rewired actions, EventSystem modules и порядок Update.
7. Контроллер движения, запрос пути, cancel, progress и видимость объектов.
8. События готового результата действия для чтения журнала и итогов хода.

Экспорт/декомпиляцию держать в `artifacts/discovery`; не включать её в публичный
архив. `TG.Main.dll` — имя сборки из внешнего inventory, не выдуманный class API.

## Шаг 4. Один binding — одна проверяемая запись

Рекомендуемый формат записи:

| Поле | Требуемое доказательство |
| --- | --- |
| `id` | Стабильное имя контракта самого мода, например `main.primary-action` |
| `assembly` | Имя, SHA-256, MVID именно исследованной сборки |
| `declaringType/member/signature` | Реально найденные тип/член и точные аргументы |
| `source` | Файл/метод оригинального UI flow, который использует этот handler |
| `readiness` | Проверка активного экрана, оконченного перехода и существования модели |
| `visibility` | Реальное правило визуальной доступности/раскрытия |
| `invoke` | Вызов original handler с оригинальной валидацией и ownership scope |
| `evidence` | Выполненный сценарий, transcript, одно действие на одно нажатие |

Условные имена из столбца `id` принадлежат моду. Их нельзя искать как реальные
классы игры или использовать в Harmony reflection без отдельной привязки.

## Шаг 5. Доказать P4 до активного UI

Проверка проводится на обратимом параметре настроек, затем на настоящем игровом
действии в тестовом забеге. Одно Enter должно дать одну активацию; повторное
удержание — ноль дополнительных покупок/карт. Отдельно испытать:

- Rewired/global keymap с присвоенным и неприсвоенным chord;
- native EventSystem selection при accessibility focus;
- input после потери фокуса, возвращения и удержания modifier;
- Enter, открывающий modal или raw keybinding screen;
- собственный вызов original handler, проходящий через ownership scope;
- StartUnfocused overlay и обычную игровую команду без accessibility cursor.

Модель из unit tests помогает проверить решение, но результат внутри игры
подтверждается счётчиком original action и изменением реального состояния.

## Шаг 6. Ошибки и обновления

Неизвестный fingerprint оставляет диагностический режим: нет догадок о targets,
массового reflection scan в каждом frame, случайной активации или бессрочного
блокирования клавиатуры. Ошибка отдельного screen build не удаляет state и
не заглушает все остальные экраны.

Если ownership hook перестал работать, соответствующий функциональный adapter
отключается целиком с однократным понятным сообщением. Он не должен продолжать
выполнять действия, надеясь, что duplicate input не произойдёт.

## Первый законченный результат интеграции

Начать с пути «старт → главное меню → настройки → изменение одного параметра →
назад». После него подключать обучение и бой. Проверка одной карты в изоляции
не снимает блокеров до боя: недоступный стартовый экран уже делает весь мод
непригодным для самостоятельного запуска.
