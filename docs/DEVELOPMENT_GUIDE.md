# Порядок разработки

Дополнение к [AGENTS.md](../AGENTS.md), адаптированное из Accessibility Mod Template.
Источник и условия: [разбор переноса](research/template-import.md).
Правила проекта и Graph A11y имеют приоритет над примерами шаблона.

## Начало и продолжение работы

1. Прочитать обязательные материалы из AGENTS и [PROJECT_STATUS.md](PROJECT_STATUS.md).
2. Определить конкретный результат текущего поручения и его место в ROADMAP.
3. Проверить записи [GAME_API.md](GAME_API.md) для затрагиваемого экрана и версии.
4. Изучать только нужные части игры. В больших файлах сначала искать через `rg`,
   затем читать найденный метод с окружающим кодом.
5. После нового открытия сразу записать доказательство; после значимого результата
   обновить PROJECT_STATUS, ROADMAP и нужную строку GAMEPLAY_COVERAGE.

Не повторять анкету первоначальной настройки: игра, Windows x64, NVDA и русский
язык уже определены. Спрашивать только недостающие сведения, которые действительно
мешают текущему действию. Невыполненная игровая проверка не запрещает независимую
работу над документацией или ядром; её статус остаётся явно незавершённым.
Длинный разговор сам по себе не требует прерывать задачу или начинать новый чат.

## До подключения игрового экрана

Проверить локальную установку и журнал загрузки по [GAME_DISCOVERY.md](GAME_DISCOVERY.md).
Нужны настоящий runtime, архитектура процесса, версия Unity, loader и отпечатки
сборок. Установленная .NET SDK и среда, в которой запускается игра, — разные вещи.
Не определять разрядность по имени каталога Mono или расположению в Program Files.
Внешние статьи и примеры дают направления поиска, но не подтверждают API Conquest.
Если найден официальный кодовый API игры, сначала проверить его возможности и
условия; не менять выбранную архитектуру без необходимости.

Для конкретного экрана должны быть установлены:

- владелец UI, момент готовности и реальные признаки открытого/покрытого экрана;
- источник видимого текста, его язык, tooltip и смысл иконок;
- оригинальные handlers действия, изменения значения, отмены и возврата;
- правила видимости, доступности, загрузки и блокировки действий;
- игровые клавиши в этом контексте и пользовательские переназначения;
- все четыре пути обработки ввода и отсутствие конфликтов NVDA/Windows;
- идентичность экземпляров и способ живого чтения при повторном открытии.

Подключать активные действия только после нужных доказательств. Непроверенное
сочетание не становится «свободным» из-за отсутствия строки в документации.
Обзор ввода/экранов/локализации обязателен до первого активного адаптера;
механику магазина, боя или исследования изучать перед соответствующей функцией.

## Одна функция за один проверяемый шаг

До изменения описать: путь игрока, ожидаемую речь, действие игры, клавиши,
зависимости, отмену, ошибки и способ проверки. Развивать интерфейс в порядке,
в котором игрок его встречает: старт, меню, настройки, обучение, бой и забег.
Для исправления сначала получить минимальный воспроизводимый сценарий и добавить
нужную поведенческую проверку. Для простой правки инструкций достаточно проверить
ссылки, согласованность требований и отсутствие неверных обещаний.

Сначала закончить один тип элемента и проверить его; затем переходить к следующему.
Результат действия озвучивать после подтверждённого изменения, а не после попытки.
Не менять сложность, правила, награды или достижения ради удобства адаптации.
Если функциональность недоступна, записать конкретное ограничение и следующий
необходимый факт, а не заменять её упрощённой игровой механикой.

## Структура и качество кода

- Оставлять диагностический plugin небольшим; отдельный адаптер отвечает за один
  экран или связанную функцию. Использовать существующие Graph, Navigator,
  ScreenManager, Localizer и InputArbitration, а не второй набор навигации.
- Следовать `.editorconfig` и текущему стилю: осмысленные имена, `_camelCase` для
  закрытых полей, понятные комментарии. У нового публичного API документировать
  назначение, аргументы, ограничения и владение ресурсами через XML `<summary>`.
- У переходов, lifetime guards и ownership объяснять причину решения. Обходной
  приём сопровождается фактом, версией, ограничением и сценарием удаления.
- Не выполнять поиск по всем объектам сцены, assembly scan или запись файла каждый
  кадр. По проверенному профилю можно хранить `MemberInfo`; живые UI-ссылки,
  render, списки и delegates игрового адаптера между кадрами не сохранять.
- Живое чтение, ввод и poll-and-diff не заменять таймером ради экономии. Тяжёлый
  диагностический экспорт выполняется по явному запросу; оптимизацию подтверждать
  измерением. Нормальный повтор клавиши не должен теряться из-за общего таймаута.
- Проверять отсутствие объекта и обычные условия явно. Исключения отражать на
  границах Build, lifecycle, внешних API и речи, сохраняя изоляцию кадра.
  Не маскировать ошибку успешным ответом, старым значением или нулём.
- Подписываться только на нужные события и освобождать собственные подписки,
  нативные ресурсы и hooks при отключении. Все обращения к Unity/UI выполнять
  в разрешённом игровом потоке и при подтверждённой готовности.

## Сборка и проверка в игре

Использовать [scripts/build.ps1](../scripts/build.ps1),
[scripts/test.ps1](../scripts/test.ps1) и [scripts/deploy.ps1](../scripts/deploy.ps1)
с их настоящими параметрами из [BUILD_AND_INSTALL.md](BUILD_AND_INSTALL.md).
Путь к игре не встраивать в общие документы или csproj. Оригинальные игровые
ссылки не копировать в результат сборки; декомпиляция не входит в исходники мода.
Не добавлять автоматическое копирование в игру после каждого `dotnet build`.

При установке или обновлении закрыть игру обычным способом, дождаться успешной
сборки, установить только файлы мода и проверить возврат к предыдущему состоянию.
Не завершать процесс насильно. В игре повторить короткий сценарий, затем возврат,
отмену, повторное нажатие и удержание клавиш с NVDA.

Если ошибка повторяется, перечитать свежий журнал и перепроверить конкретный
handler/версию. После нескольких неудачных попыток изменить проверяемую гипотезу,
описать подтверждённые факты и продолжить доступную независимую работу. Не менять
загрузчик, игровые DLL или широкие перехваты ввода в качестве случайного обхода.

Завершение работы содержит результат, выполненные проверки и практическое
ограничение. Статусы `implemented`, `portable-tested`, `compiled-with-game`,
`in-game-tested`, `blind-user-accepted` записываются раздельно.
