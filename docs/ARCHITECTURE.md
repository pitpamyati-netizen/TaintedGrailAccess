# Архитектура

## 1. Граница готового кода

Проект использует собственную параллельную модель интерфейса из пользовательского
[Graph A11y Draft 1](spec/graph-a11y-spec.original.md). Это самостоятельная
реализация спецификации, не копия исходников RTAccess/WrathAccess.

| Компонент | Ответственность | Фактический статус |
| --- | --- | --- |
| `TaintedGrailAccess.Graph` | Узлы, идентичность, связи, builder, cursor, операции, компоновка текста | Реализован; отдельно компилируется; поведенческие тесты |
| `TaintedGrailAccess.Runtime` | Навигатор, речевая политика, экраны, локализация, модель ownership | Реализован; проверен на изменяемых fake screens |
| `TaintedGrailAccess.Windows` | NVDA controller, необязательный Tolk, SAPI, transcript-only | Реализован; сборка и безопасные отказы проверены; настоящий звук не проверен |
| `TaintedGrailAccess.BepInEx` | Диагностический Mono plugin, startup log, export signatures | Исходник подготовлен; требует игровых/loader refs и проверки в игре |
| Будущий Conquest adapter | Живые модели, экраны, handlers, Rewired/EventSystem, перемещение | Не реализован; неизвестные имена API не подставлены |

Основные библиотеки имеют целевой `netstandard2.0`, C# 7.3. Тестовый процесс —
`net8.0`. Это разные среды: запуск теста .NET 8 не доказывает загрузку плагина
под Unity Mono. Mono host — выбранная ветвь для первоначальной проверки;
если локальная игра IL2CPP, нужен отдельный host, а не изменение ядра.

## 2. Порты из дополнения

| Порт | В проекте | Что ещё доказать в Conquest |
| --- | --- | --- |
| P1 State read | Build и живые delegates в `NodeVtable` | Источники данных, дешёвое чтение, правила видимости, время жизни моделей |
| P2 Action invoke | Поведенческие slots и `EnterOwnAction` | Точный оригинальный handler каждого действия и его предусловия |
| P3 Tick | `AccessibilityRuntime.Update`; диагностический Unity Update | Настоящий порядок вызовов относительно input/game ticks |
| P4 Key input/arbitration | `KeyChord`, consumed-contract, `InputArbitration` | Физический capture, Rewired, EventSystem, exclusivity, key-up/repeat |
| P5 Speech | `ISpeechOutput`, Windows backend | Реальный NVDA/JAWS/SAPI, архитектура DLL, очередь и отмена |
| P6 Sound | `ISoundOutput`, opaque sound slots | Существующие звуки игры и отсутствие их дублирования |
| P7 Localization | `Localizer`, `locales/*.properties`, startup tables | Подключение к настройке языка игры и семантика её icon text |
| P8 Settings | Фильтр type/kind, позиции; BepInEx diagnostic config | Сохранение всех пользовательских параметров и доступный settings screen |
| P9 Logging | Focus trace API, изоляция ошибок, diagnostic speech transcript | Доступный пятистрочный журнал/полный обзор и корреляция игровых событий |

**Наличие P4-модели не означает, что ввод уже подавлен внутри игры.** До проверки
реальных четырёх путей production navigator в host не подключается.

## 3. Одноразовые деревья и постоянный курсор

Экран объявляет `GraphBuilder` заново из текущего состояния. Перед каждой
операцией `KeyGraph` строит новый render. В state остаются только курсор,
предыдущий порядок, запрос фокуса, память остановок и развёрнутые группы.

`ControlId` использует structural key для hash/equality, а ссылку — как отдельный
первый уровень восстановления. Это существенно для руки карт: две одинаковые
карты имеют разные экземпляры; один экземпляр может сменить место, стоимость,
сторону или представление. Ключ вида `card.name` не уникален; ключ `hand[2]`
не следует за перемещённой картой. Используется подтверждённый game instance id
с run/battle scope и ссылка на настоящую domain model, когда она существует.

Переиспользуемый Unity view не является надёжной идентичностью карты. Ссылка
на уничтоженный Unity object требует корректной проверки жизненного цикла
адаптером; оператор Unity `== null` и `ReferenceEquals` решают разные задачи.

Если объект исчез, фокус идёт назад по прежнему порядку к ближайшему выжившему,
затем использует selected member/start. Покрытый диалогом экран хранит свой
state; закрытый экран начинает заново, если не включён KeepStateOnPop.

MemberInfo и проверенные описания binding можно кешировать по профилю сборки.
Кешировать дерево, старый список целей или текст стоимости между кадрами нельзя.
Не сканировать все Unity объекты и свойства каждый кадр: после discovery нужно
обращаться к конкретному владельцу соответствующего состояния.

## 4. Единственный источник фокусной речи

`Navigator.AnnounceLanding` — общий путь для прямой навигации и frame differ.
Он сравнивает цепочки структурных родителей, произносит новый контекст и сам
элемент, сохраняет identity и перебазирует Live-watch.

- Нажатие стрелки, Tab или результат поиска прерывают прошлую речь.
- Имя нового экрана и автоматическое восстановление фокуса ставятся в очередь.
- Изменение Live value у текущего элемента читает только изменившуюся часть.
- StateText после синхронного toggle/slider подавляет повтор того же Live change.
- Ошибка необязательного звука не должна приводить к повтору уже сказанного фокуса.

`GraphAnnouncer` только возвращает строки. В ядре нет NVDA, Win32, очереди
произнесения или вызова Speak. Короткие подписи соответствуют визуальному
контролу; полный tooltip вызывается отдельным verb.

Игровой адаптер передаёт локализованный обычный текст. Unity/TMP rich text
нормализуется на границе чтения: форматирование удаляется, значимые иконки
получают проверенные текстовые имена. Нельзя механически удалять значок энергии,
если он несёт смысл; нельзя превращать `< 3` в потерянное математическое условие.
Встроенный search stripper решает поиск, а не всю семантику игровых rich strings.

## 5. Ввод: четыре независимых пути

1. Poller мода переводит физические события в `KeyChord`. Он учитывает focus
   окна, модификаторы, OS repeat, layout и release. Insert/CapsLock не назначаются.
2. Патчи игрового keymap/Rewired проверяют только consumed chords текущего
   кадра. Где есть штатная перенастройка, конфликт лучше разрешить через неё.
3. EventSystem/Submit или original handler получает ownership guard. Во время
   вызова от мода `EnterOwnAction` пропускает оригинальное действие, а физическая
   повторная активация остаётся заблокирована.
4. Mod-owned modal при установленном фокусе эксклюзивен. Raw binding capture
   и настоящее текстовое поле оставляют ввод своему владельцу.

Реальный host обязан обеспечить capture раньше game input. Один Harmony postfix
после уже произошедшей покупки не отменяет покупку. Общий `Input.ResetInputAxes`,
отключение Rewired целиком или очистка всего input каждый frame ломают contextual
verbs и не являются реализацией этого контракта.

`consumed=true` сохраняется, даже если прочитать состояние после действия
не удалось. Клавиша, открывшая raw capture, остаётся присвоенной до конца
текущего кадра и не должна тут же назначить саму себя в новом диалоге.
На следующем кадре raw capture работает без перехвата.

## 6. Жизненный цикл

`ScreenManager` опрашивает IsActive, выбирает верхний корневой screen по Layer
и его самый глубокий активный child. Активный child без активного parent
не участвует. Регистрация стабильна; равный Layer разрешается порядком регистрации.
После OnUpdate проводится повторная сверка перед первым нажатием кадра.

После действия runtime снова сверяет экраны: карточный выбор может создать
target modal, а подтверждение — reward screen. Следующая клавиша должна попасть
в новый контекст. Screen predicates и Build изолируются; ошибка логируется
один раз на пару screen/type, а не на изменяющийся текст исключения.

`Dispose` runtime освобождает ownership и состояния. Будущий host также снимает
только свои Harmony hooks и возвращает изменённое native selection/input state.
Diagnostic host не устанавливает hooks, поэтому это пока обязательство адаптера.

## 7. События боя и обзор

Игровой event narrator ещё нужно реализовать. Он получает завершённые изменения
из проверенных UI/event flows: разыграна карта, нанесён видимый урон, изменён
ресурс, получен статус, начался ход. Нельзя читать всю сцену или весь HUD каждый
кадр и выдавать это за журнал.

Идентичность события включает сессию/бой и оригинальный event/transaction id,
если он существует. Не устранять дубликаты по таймауту: два одинаковых удара
могут быть разными настоящими событиями. Группировать следует один подтверждённый
пакет разрешения действия. Критические исходы не теряются при сокращении.
Обычный обзор — последние пять строк, полный буфер — отдельно; текущая карта
не теряет фокус при чтении статуса или истории.

## 8. Перемещение — отдельная подсистема

Сканер выбирает только объекты, которые визуальная игра сейчас разрешает знать.
Выбор в сканере не двигает героя. Команда движения передаёт цель штатному
controller/pathfinder, проверяет достижимость и наблюдает реальный прогресс.
Она отменяется пользователем, при ручном движении, потере фокуса окна,
начале боя/диалога, смене сцены или исчезновении цели.

Наличие AstarPathfindingProject/NavMeshComponents в depot — только ориентир для
discovery. Не считать это готовым подтверждением `NavMeshAgent.SetDestination`.
Не менять transform.position и не обходить препятствия/скрытые области.
Если карта предполагает самостоятельное раскрытие, нужен доступный способ
исследовать границу известной области; один список уже известных NPC недостаточен.

## 9. Проверки и дальнейшее расширение

Независимые библиотеки собираются отдельно: нарушение engine/kernel boundary
ломает сборку Graph tests. Сценарии Runtime используют изменяемые models,
изменение экранов и ошибки после действия. В Windows suite проверяется честный
отказ, а не слышимость. [TEST_RESULTS.md](TEST_RESULTS.md) фиксирует реальные
результаты; [ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md) определяет игровые gates.

Новые features добавляются конкретным screen adapter с собственным acceptance
сценарием. Универсальный scanner всех Unity Button не заменяет ни combat adapter,
ни анализ видимости, ни управление процедурной картой.
