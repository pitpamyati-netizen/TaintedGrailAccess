# Подготовка пользовательского выпуска

Адаптация distribution-guide из Accessibility Mod Template;
[источник и условия](research/template-import.md).
Создание репозитория с исходниками не означает выпуск готового мода.
Выпуск, установка, обновление сервиса или сообщение в стороннее сообщество
выполняются по соответствующему поручению пользователя.

## Условия готовности

- Есть проверенный профиль конкретной Conquest: магазин, build ID при наличии,
  runtime, архитектура, Unity/loader и SHA-256/MVID игровых сборок.
- Выполнены нужные пункты M6, игровые проверки и приёмка слепым пользователем.
  В описании отдельно указаны implemented/portable-tested/compiled-with-game/
  in-game-tested/blind-user-accepted; ограничения видны до скачивания.
- Установка, обновление, отключение и возврат проверены с клавиатуры. Существующий
  чужой загрузчик не заменяется. Игровые файлы и сохранения не изменяются установщиком.
- Поддержка NVDA подтверждена настоящей речью и повторным вводом. JAWS/Tolk/SAPI
  называются проверенными только при наличии отдельных сценариев и результатов.

Текущий проект этим условиям ещё не соответствует: игровые bindings отсутствуют.
Работающий стартовый голос и переносимые тесты не дают основания объявлять 1.0.

## Состав пакета

Пользователю не нужны SDK, декомпилятор и игровые reference assemblies. В пакет
включать только построенные файлы самого мода, реально нужные локализации,
публичный профиль без личных путей, инструкцию, изменения версии и лицензии.
Для текущей ветви Mono файлы plugin размещаются по правилам BepInEx, описанным
в BUILD_AND_INSTALL; папка `Mods/` из примеров MelonLoader сюда не переносится.

Внешние loader/native библиотеки включать лишь после проверки точного комплекта,
архитектуры и условий распространения с его notices. Если они не включены,
дать прямые официальные ссылки и ясные отдельные шаги. Tolk не делать обязательным
для прямого NVDA пути. Системные DLL Windows не прикладывать.

Нельзя включать игровые DLL/exe/assets, декомпиляцию, сохранения, личные конфиги,
логи, исходный архив шаблона, временные файлы, bin/obj и инструменты разработки.
Просмотреть архив перед публикацией: список и размер файлов, лицензии, отсутствие
личных путей, контрольные SHA-256 и совпадение версии с описанием.
Само наличие `.gitignore` не гарантирует безопасный состав release ZIP.

## Инструкция для игрока

Подготовить короткую линейную `README.txt` в UTF-8 без таблиц и ASCII-рисунков:

1. Что именно доступно и что ещё ограничено; точные проверенные версии.
2. Требования: игра, загрузчик, Windows x64, проверенный скринридер/канал.
3. Установка по шагам, с правильным каталогом каждого файла и закрытой игрой.
4. Первый запуск и ожидаемое сообщение; короткая проверка меню и одного действия.
5. Клавиши и доступная помощь, настройки подробности и речи, проверенные конфликты.
6. Обновление, отключение и возврат; куда обращаться с очищенным отчётом об ошибке.
7. Что проверить, если мод не загружается, речь отсутствует или версия неизвестна.

Не обещать «все меню доступны» по результату одного экрана. Не требовать зрячего
помощника для обычной установки и управления; непроверенный шаг помечать явно.

## Версии, изменения и GitHub

Использовать согласованную `MAJOR.MINOR.PATCH`: несовместимые изменения,
новые функции, исправления. Версия plugin, package, tag, README и CHANGELOG
совпадает. Описание изменения говорит, что теперь может сделать игрок,
какая ошибка исправлена и на какой версии это проверено.

Перед публикацией выполнить нужные проверки, собрать пакет из проверенного кода,
сверить содержимое и описание. На GitHub приложить сам пакет, checksum и сведения
о совместимости. После загрузки сверить удалённые файлы и checksum с локальными.
Доступность исходников на GitHub и готовый пользовательский release учитываются
раздельно. Не создавать release автоматически после обычного коммита.

После обновления игры следовать DIAGNOSTICS: неизвестный профиль остаётся
диагностическим, совместимость перепроверяется. Записать проверенную версию
вместо неограниченного обещания поддержки будущих обновлений.

## Предложение разработчикам игры

Если пользователь поручит обратиться к разработчикам, сначала подготовить
работающий пример, ясное описание пользы, независимые модули, документацию,
проверки, лицензии и отзыв слепых игроков. Использовать опубликованный канал
обращений и ссылку на исходники. Не выдавать техническую возможность мода за
согласие правообладателя и не отправлять сообщение без поручения.
