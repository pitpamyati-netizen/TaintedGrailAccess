# Сборка, диагностика и отключение

## Что можно получить из этого архива

Исходный архив предназначен для разработки. Независимые Graph, Runtime и Windows
собираются отдельно от игры. Диагностический host можно собрать только с локальными
ссылками на совместимый BepInEx 5 и Unity Mono. Он проверяет запуск и речевой канал,
и в версии 0.1.1 пассивно читает стартовую подсказку на GOG 1.61.
Управление меню, подавление ввода, бой и перемещение ещё не подключены.
Версия 0.1.2 дополнительно содержит отключённое по умолчанию наблюдение за
обработкой ввода; подавление клавиш остаётся неподключённым. Она собрана с
игровыми ссылками, но новая установка, запуск и NVDA ещё не проверены.

Подтверждены GOG 1.61 / Unity 2020.3.23f1 / Mono / Windows x64 и слышимость
первого текста через NVDA. Другие версии и игровые действия ещё не поддерживаются.
Наличие `mono_likely` в инвентаризации означает статические свидетельства, а не
успешную загрузку мода. Точный порядок исследования описан в
[GAME_DISCOVERY.md](GAME_DISCOVERY.md), а фактические результаты подготовки архива —
в [TEST_RESULTS.md](TEST_RESULTS.md).

## 1. Рабочая папка и необходимые компоненты

Распакуйте архив в отдельную папку, например `C:\Mods\TaintedGrailAccess`.
Откройте её в Codex, укажите задачу и настоящий путь к установленной Conquest.
Правила — в [AGENTS.md](../AGENTS.md) и [DEVELOPMENT_GUIDE.md](DEVELOPMENT_GUIDE.md). Все команды ниже выполняются
из корня проекта. Пути к игре и DLL в примерах нужно заменить своими.

Для обычных проверок нужны установленный .NET SDK 8 или новее, runtime .NET 8,
Python 3.9 или новее
и PowerShell 5.1 или новее. Unity Editor и Visual Studio не обязательны.
Скрипты не устанавливают SDK, загрузчик или библиотеки дикторов автоматически.
Первый обычный build может обратиться к NuGet за официальными reference packages
для `netstandard2.0`. Сами тесты не используют NUnit, xUnit или игровые DLL.

Полезные первичные страницы: [.NET 8 SDK](https://dotnet.microsoft.com/en-us/download/dotnet/8.0),
[Python для Windows](https://www.python.org/downloads/windows/),
[NETStandard.Library 2.0.3](https://www.nuget.org/packages/NETStandard.Library/2.0.3).
Версия SDK, на которой подготовлен отчёт архива, — 8.0.425; это описание проверки,
а не требование установить именно этот patch.

## 2. Проверка независимого кода

Обычный запуск собирает три набора C#-тестов и запускает Python-тесты:

```powershell
.\scripts\test.ps1
```

Обычный вывод краткий. Для подробностей:

```powershell
.\scripts\test.ps1 -Verbose
```

Журналы находятся в `artifacts/logs/tests`. Любая ошибка завершает скрипт ненулевым
кодом. Успех этих тестов подтверждает независимую модель интерфейса, а не работу
мода с установленной игрой или слышимую речь NVDA.

Если доступ к NuGet отсутствует, а .NET SDK с reference/runtime packs .NET 8 уже
полностью установлен:

```powershell
.\scripts\test.ps1 -Offline
```

Этот режим создаёт локальную конфигурацию NuGet без источников и временно задаёт
`GraphTargetFramework=net8.0` для независимых библиотек. Он проверяет их поведение
на .NET 8. Production-совместимость с `netstandard2.0` и игровой host проверяются
отдельно. Конфигурация пользователя и глобальные источники NuGet не меняются.

Чтобы получить три независимые библиотеки с production target:

```powershell
.\scripts\build.ps1 -Target Core
```

Результат: `artifacts/core`, три собственные DLL и две таблицы локализации.
Это библиотеки для разработки; загрузочного плагина в Core-пакете нет.

### Проверка через компилятор SDK без MSBuild и NuGet

В среде подготовки архива стандартный CLI .NET не запускался из-за ограничения
системной информации о процессе. Поэтому проверка выполнена непосредственно
компилятором Roslyn из официального SDK, без подставных Unity/BepInEx типов.
Этот воспроизводимый маршрут включён в проект:

```powershell
py -3 .\scripts\verify_core.py --sdk-root "C:\Program Files\dotnet"
```

Скрипт находит установленный SDK 8.x, компилирует отдельные библиотеки, запускает
тестовые executable на .NET 8 и Python-тесты. По умолчанию библиотеки в этом режиме
также проверяются против .NET 8. Для отдельной проверки production API укажите
папку `build/netstandard2.0/ref` из официального пакета NETStandard.Library 2.0.3:

```powershell
py -3 .\scripts\verify_core.py --sdk-root "C:\Program Files\dotnet" --netstandard-ref "C:\ReferencePackages\NETStandard.Library.2.0.3\build\netstandard2.0\ref"
```

Этот вариант с production references применён при подготовке архива.
Параметр `--output` задаёт отдельную папку результатов; стандартная папка —
`artifacts/verification`. Машиночитаемый отчёт — `verification.json`.
Тестовые бинарные файлы из этой папки в игру не устанавливают.

## 3. Определение установленной игры

```powershell
py -3 .\scripts\inspect_game.py --game-dir "D:\SteamLibrary\steamapps\common\Tainted Grail"
```

Инструмент читает только выбранную установку и пишет отчёт вне папки игры.
Он проверяет характерные пути, заголовки PE/CLI, архитектуру и SHA-256.
Образец имени EXE — `Tainted Grail.exe`, папки данных — `Tainted Grail_Data`.
Это требуется сопоставить с фактической копией, а не создавать отсутствующие
файлы или переименовывать другую игру ради прохождения проверки.

Для сопоставления с конкретным Steam-манифестом:

```powershell
py -3 .\scripts\inspect_game.py --game-dir "D:\SteamLibrary\steamapps\common\Tainted Grail" --appmanifest "D:\SteamLibrary\steamapps\appmanifest_1199030.acf"
```

Сам inspector собирает свидетельства. Скрипты диагностической сборки и установки
дополнительно требуют соответствия `installdir` выбранной папке. App ID Conquest —
1199030; описание продукта: [официальная страница игры](https://store.steampowered.com/app/1199030/Tainted_Grail_Conquest/).
Сопоставление манифеста не удостоверяет все исполняемые файлы и не заменяет
проверку `Application.productName`, Unity/runtime и журнала запуска.

При IL2CPP, смешанных свидетельствах, неоднозначных путях или неподходящей
архитектуре диагностическая сборка этого host останавливается. Нужно исследовать
другую конфигурацию загрузчика; нельзя подставлять `true` в неподтверждённый профиль.
Официальные инструкции BepInEx различают
[Mono и другие варианты установки](https://docs.bepinex.dev/articles/user_guide/installation/index.html)
и [Unity IL2CPP](https://docs.bepinex.dev/master/articles/user_guide/installation/unity_il2cpp.html).

## 4. Подготовка диагностического host

Для ветки Windows x64 / Unity Mono используйте совместимый BepInEx 5,
полученный отдельно из официального проекта. Сначала проверьте уже установленный
загрузчик и его журнал. Существующие BepInEx, Doorstop и чужие моды не следует
заменять ради сборки проекта. Этот архив не содержит собственного установщика
загрузчика.

Сборка для обычной Steam-установки:

```powershell
.\scripts\build.ps1 -Target Diagnostics -GameDir "D:\SteamLibrary\steamapps\common\Tainted Grail"
```

Скрипт ищет соседний `appmanifest_1199030.acf`. Если нужен явный путь, добавьте
`-AppManifest "D:\SteamLibrary\steamapps\appmanifest_1199030.acf"`.
Для отдельной копии или другого магазина укажите `-NonSteam` вместо
`-AppManifest`:

```powershell
.\scripts\build.ps1 -Target Diagnostics -GameDir "D:\Games\Tainted Grail" -NonSteam
```

`-NonSteam` снимает только требование соответствующего Steam-манифеста.
Проверки PE x64, признаков Mono и локального BepInEx 5 сохраняются. Название
продукта и фактическую совместимость надо подтвердить в журнале игры.
Каталоги со ссылками или junction скрипты не обрабатывают автоматически.

Проект использует локальные `BepInEx/core/BepInEx.dll`,
`Tainted Grail_Data/Managed/UnityEngine.CoreModule.dll`, `UnityEngine.UIModule.dll`,
`BepInEx/core/0Harmony.dll` и, если присутствует, `UnityEngine.dll`.
Эти DLL помечены как внешние ссылки и не копируются в пакет.
Конкретная сборка Unity может потребовать уточнения references после исследования;
host 0.1.1 скомпилирован с файлами исследованной GOG 1.61 без предупреждений.

Успешная сборка создаёт `artifacts/package/TaintedGrailAccess` с четырьмя
собственными DLL и `locales/en.properties`, `locales/ru.properties`.
Рядом, вне устанавливаемой папки, появляется `diagnostic-package.json` с SHA-256
пакета и использованных файлов игры/загрузчика, включая Harmony и Unity UI.
Неудачная повторная сборка
не оставляет старый манифест пригодным для автоматической установки.

## 5. Установка и первый диагностический запуск

Закройте игру. Для Steam-установки:

```powershell
.\scripts\deploy.ps1 -GameDir "D:\SteamLibrary\steamapps\common\Tainted Grail"
```

Параметры `-AppManifest` и `-NonSteam` применяются так же, как при сборке.
Скрипт проверяет манифест пакета, состав файлов, их SHA-256 и соответствие выбранной
игры той, с которой собирался host. После обновления используемых игровых или
загрузочных файлов требуется повторная сборка.

Устанавливается только `BepInEx/plugins/TaintedGrailAccess`. При обновлении
распознанная прежняя папка копируется в `artifacts/backups` проекта; состав и
hashes копии проверяются перед заменой. Если установка прерывается после удаления
прежней папки, скрипт пытается восстановить её и сообщает путь проверенной копии.
Установка 0.1.0 и обновление до 0.1.1 с проверенной копией испытаны на Windows.
Восстановление после аварийного прерывания ещё не испытывалось.

Запустите игру обычным способом с уже запущенной NVDA. Плагин создаёт конфигурацию:

```text
BepInEx/config/org.taintedgrailaccess.diagnostics.cfg
```

На первом запуске путь NVDA DLL пуст, поэтому `auto` может выбрать запасной
системный голос SAPI или только журнал. Для проверки именно NVDA закройте игру,
получите официальный x64 NVDA Controller Client отдельно, затем задайте:

```ini
[General]
Language = ru

[Speech]
Backend = nvda
NvdaDllPath = C:\Accessibility\NVDA\nvdaControllerClient64.dll
TolkDllPath =
AllowSapiFallback = false

[Diagnostics]
ExportAssemblyInventory = false
```

Путь должен указывать на реально полученную DLL x64. Источник и описание ABI:
[NVDA Controller Client](https://github.com/nvaccess/nvda/blob/master/extras/controllerClient/readme.md).
Наличие экспорта в DLL само по себе не подтверждает её происхождение.
Запасной голос выключен в этом примере, чтобы приёмка NVDA не засчитала речь SAPI.
Для обычного резервирования можно затем вернуть `Backend = auto` и
`AllowSapiFallback = true`.

Первый пассивный адаптер включается `Accessibility.ReadStartPrompt = true`.
Он требует GOG 1.61, Unity 2020.3.23f1 и точного SHA-256/MVID TG.Main из GAME_API.
При несовпадении adapter не устанавливает hook и остаётся диагностика.
`ReadStartPrompt = false` возвращает режим только стартовой проверки речи.
Клавиши у этого адаптера не назначены: подсказку закрывает обычное управление игры.
Для текущей разработки bridge хранится в игнорируемой `local/speech`, отдельно
от очищаемых результатов сборки. Его личный путь есть только в локальном cfg.

В 0.1.2 можно отдельно включить одноразовую проверочную запись
`Diagnostics.ObserveTitleInput = true`. После старта флаг сбрасывается;
наблюдение заканчивается после 600 записей. Original input не блокируется,
игровые действия модом не вызываются. Инструкция и ограничения —
[DIAGNOSTICS.md](DIAGNOSTICS.md#наблюдение-ввода-стартового-меню-012).
Для сборки нужны также локальные UnityEngine.InputLegacyModule и IMGUIModule;
они используются как ссылки, в пакет не копируются. build/deploy сверяют их hash.

На исследованной сборке 0.1.1 стартовая фраза сообщает о доступном чтении
первой подсказки и неподключённом управлении меню. На неизвестной сборке
сохраняется диагностическая фраза. Речь произносится после получения игрой фокуса.
Озвученная стартовая фраза подтверждает только этот канал. Проверьте отдельно
слышимость, прерывание, очередь и поведение после Alt+Tab по
[ACCEPTANCE_TESTS.md](ACCEPTANCE_TESTS.md).

Для JAWS предусмотрен необязательный `Backend = tolk` и абсолютный путь
`TolkDllPath`. Tolk и его нужные backend-зависимости получают отдельно;
эта комбинация ещё не проверена. `Backend = sapi` использует системный голос,
а `Backend = transcript` намеренно пишет только текстовый журнал.

## 6. Журналы и экспорт для поиска bindings

Под папкой плагина создаётся `diagnostics/diagnostic.log`.
Записи `speech.request` означают запрос речи; даже успешный ответ API не доказывает,
что пользователь услышал текст. Для ошибки сравнивают этот журнал, журнал BepInEx
и то, что действительно услышано.

Для одноразового экспорта сигнатур задайте
`ExportAssemblyInventory = true` при закрытой игре и запустите её заново.
Флаг сбрасывается после попытки. Файл — `diagnostics/assembly-signatures.txt`.
Экспорт ограничен `TG.Main` и `Assembly-CSharp`, не собирает значения игровых полей,
состояние сцены, содержимое сохранений, будущие карты или скрытые награды.
Сигнатуры нужны для локального исследования; сами по себе они не подтверждают
назначение handler. Инструкции для нового binding — в GAME_DISCOVERY.

Публичный отчёт об ошибке составляйте по [ISSUE_TEMPLATE.md](ISSUE_TEMPLATE.md).
Перед передачей диагностических файлов проверяйте личные пути и ненужные данные.
Игровые DLL и декомпилированную игру в дистрибутив не добавляют.

## 7. Отключение и восстановление

Закройте игру и выполните:

```powershell
.\scripts\deploy.ps1 -GameDir "D:\SteamLibrary\steamapps\common\Tainted Grail" -Disable
```

Отключение переносит распознанную папку нашего плагина в проверенную резервную
копию под `artifacts/backups`. Для этого не нужны Python, SDK, Steam-манифест
или совпадение runtime с прошлой сборкой. Обновление игры не должно блокировать
возможность убрать собственный плагин. Если папки уже нет, действие завершается
успешно без изменений.

Путь копии выводится в консоль. Для ручного возврата при закрытой игре убедитесь,
что `BepInEx/plugins/TaintedGrailAccess` отсутствует, и скопируйте сохранённую
папку `TaintedGrailAccess` в `BepInEx/plugins`. Возвращать предыдущую DLL имеет
смысл только с той версией игры и загрузчика, с которой она была проверена.
Конфигурация плагина хранится отдельно в `BepInEx/config` и сохраняется при
отключении; чужие моды, загрузчик и игровые сохранения не удаляются.

Если папка не распознана как собственный плагин или найдены ссылки, скрипт
оставляет её без изменений и объясняет причину. Не переименовывайте чужие DLL,
чтобы обходить такую проверку.

## 8. Следующий результат, который нужно доказать

После первого чтения Codex должен подключить управление настоящим экраном с реальными
предикатами видимости и исходными обработчиками, затем проверить все четыре
пути ввода. Только после этого можно переходить к полному циклу, описанному в
[GAMEPLAY_COVERAGE.md](GAMEPLAY_COVERAGE.md). Сборка, запуск host, проверка NVDA,
работа игрового экрана и приёмка незрячим игроком отмечаются отдельно.
